# What you’re building (in plain terms)

* Users upload **big files** from the browser.
* A **backend worker** processes them (may be a different service than the upload API).
* The UI shows **live progress 1%…100%**.
* When done, the UI gets an **auto-download link**.

# Low-cost (Free-Tier-friendly) Reference Architecture

* **Frontend:** Static app (React/Next, etc.) on **S3 + CloudFront** (or Amplify Hosting if you prefer).
* **Auth (optional but recommended):** **Amazon Cognito** (Hosted UI; cheapest sane option).
* **Upload storage:** **Amazon S3** (multipart, resumable; presigned URLs from backend).
* **Job queue:** **Amazon SQS** (standard queue).
* **Coordinator API:** **API Gateway (HTTP)** + **Lambda** to:

  * issue **presigned upload URLs**
  * **enqueue jobs** after upload
  * **return a jobId** to the client
* **Progress channel:** **API Gateway (WebSocket)** + **Lambda**; client subscribes with `jobId`.
* **State store:** **DynamoDB** table `Jobs` (PK=`jobId`) holding `{status, percent, outputKey, connectionId}`.
* **Worker:** **AWS Lambda** (for light/medium CPU tasks, ≤15 min) **or** **Fargate (ECS)** for heavier/longer jobs.

  * Worker pulls from SQS, processes file in **chunks**, updates DynamoDB `%`, and pushes updates to WebSocket.
* **Notifications:** Optional **SNS** if you want fan-out or emails; otherwise worker talks straight to WebSocket.
* **Result download:** Worker writes result to S3 and the API issues a **presigned download URL**; UI auto-downloads.

> Why this stack? It’s serverless (cheap, managed), supports WebSockets, scales horizontally, and keeps each piece simple.

# Data/Control Flow (happy path)

1. **Frontend** asks the HTTP API for an **upload URL** → gets `{uploadUrl, fileKey, jobId}`.
2. Browser **uploads directly to S3** using the presigned URL (no backend bandwidth).
3. Frontend calls **/startJob** with `jobId` & `fileKey` → API enqueues to **SQS**.
4. Frontend opens **WebSocket** (API GW WS) and sends `{action:"subscribe", jobId}` to register for progress.
5. **Worker** (Lambda/ECS) receives job from SQS, updates DynamoDB `{percent: 1..100}` as it proceeds, and pushes messages to the WebSocket route (`@connections`) like `{jobId, percent, status}`.
6. On completion, worker writes **output** to S3, updates `status="DONE"`, and pushes `{percent:100, downloadUrl:<presigned>}`.
7. **Frontend** receives that and **auto-downloads**.

# Step-by-Step Build (minimal, Free-Tier)

## 0) Prereqs

* An AWS Free Tier account, IAM admin (for setup), Node 18+, AWS CLI configured.
* Region: pick one (e.g., `us-east-1`) and stick with it.

## 1) S3 buckets

* Create two buckets:

  * `myapp-uploads-<account>-<region>`
  * `myapp-outputs-<account>-<region>`
* Turn on **Block Public Access** for both.
* Add CORS to the *uploads* bucket (adjust origins):

```json
[
  {
    "AllowedOrigins": ["https://your-frontend-domain.com","http://localhost:3000"],
    "AllowedMethods": ["PUT","POST","GET"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag","x-amz-request-id","x-amz-id-2"]
  }
]
```

## 2) DynamoDB

* Table: `Jobs`

  * **PK**: `jobId` (string)
  * Attributes: `status` (S), `percent` (N), `fileKey` (S), `outputKey` (S), `connectionId` (S), `updatedAt` (N)

## 3) SQS queue

* `myapp-jobs` (Standard).
* Dead-letter queue optional but good (`maxReceiveCount: 3`).

## 4) API Gateway (HTTP) + Lambdas

Create 3 Lambdas:

* `getUploadUrl` (returns `{jobId, fileKey, uploadUrl}` using `s3.getSignedUrl('putObject')`).
* `startJob` (validates the fileKey belongs to jobId; enqueues message to SQS).
* `getDownloadUrl` (optional fallback: returns presigned GET if needed).

IAM for these Lambdas:

* Read/Write to DynamoDB `Jobs`.
* `s3:PutObject` on uploads bucket only via **presign** (runtime needs `s3:PutObject` for the signer).
* `sqs:SendMessage` to `myapp-jobs`.

Routes (HTTP API):

* `POST /upload-url`
* `POST /start-job`
* `GET /download-url?jobId=...` (optional)

## 5) API Gateway (WebSocket) + Lambdas

Create WS API with routes:

* `$connect` → `wsConnect` Lambda: on connect, do nothing; you’ll map connection at subscribe time.
* `$disconnect` → `wsDisconnect` Lambda: remove `connectionId` from any job that used it.
* `subscribe` (custom route) → `wsSubscribe` Lambda: body `{"action":"subscribe","jobId":"..."}`; it writes `connectionId` to the job item in DynamoDB.

Give workers a way to post to clients:

* Workers will call **ApiGatewayManagementApi** `postToConnection({ConnectionId, Data})`.

## 6) Worker

**Option A (Free-tier/simple): Lambda worker**

* Trigger: SQS `myapp-jobs`.
* Handler outline:

  1. Mark job `status="RUNNING", percent=1`.
  2. Stream the input from S3 (use range reads if needed), process in **N chunks**.
  3. After each chunk, compute `percent = floor(processedChunks/N * 100)`, `UpdateItem` in DynamoDB, and `postToConnection` over WS.
  4. Write result to `outputs` bucket (optionally multipart).
  5. Generate **presigned GET** URL for `outputKey` (valid e.g., 15 min).
  6. Update `status="DONE", percent=100, outputKey`.
  7. Push final WS message `{jobId, status:"DONE", percent:100, downloadUrl:<url>}`.

**Option B (heavier/longer): ECS Fargate worker**

* Create an SQS-polling single-task service (min=0 or 1 tasks to save cost).
* Task role allows S3 get/put, DynamoDB, and ApiGatewayManagementApi.
* Same logic as Lambda, but with no 15-min cap.

## 7) Frontend (React/Next or your choice)

* On “Select file”:

  1. `POST /upload-url` with `{filename, size, contentType}` → receive `{jobId, fileKey, uploadUrl}`.
  2. Upload file **directly to S3** with `PUT uploadUrl` (or multipart for very large files).
  3. `POST /start-job` with `{jobId, fileKey}`.
  4. Open WebSocket to `wss://<your-ws-api-id>.execute-api.<region>.amazonaws.com/prod` and send `{"action":"subscribe","jobId":"..."}`.
  5. Display progress as messages arrive:

     * Example WS message: `{"jobId":"...","percent":42,"status":"RUNNING"}`
  6. When `status==="DONE"`, call `window.location = downloadUrl` (or `a.download` trick) to auto-download.

> Tip: For **really large** uploads (>5GB), use **S3 Multipart Upload** on the client with the presigned-parts approach.

export const handler = async (event) => {

    statusCode: 200,
    body: JSON.stringify({ jobId, fileKey, uploadUrl })

};

# Alternatives & when to use them

### Realtime channel

* **API GW WebSockets** (chosen): simple, serverless, per-connection billing.
* **AppSync GraphQL Subscriptions:** easiest DX if you like GraphQL; integrates auth/Cognito nicely.
* **AWS IoT Core (MQTT over WebSockets):** large-scale pub/sub; great for many devices, a bit more setup.
* **Server-Sent Events (SSE):** cheap over plain HTTP, but API GW doesn’t support native SSE; you’d need ALB/ECS/EC2.

### Orchestration

* **AWS Step Functions** to model multi-stage pipelines and progress:

  * Standard (long-running, at-least-once) or Express (cheap, high-throughput).
  * Each Task updates DynamoDB `%` and sends WS messages.
* **EventBridge** for decoupled events (job.started, job.progress, job.completed).

### Workers

* **Lambda** (<=15 min, memory up to 10GB, ephemeral disk up to 10GB+): cheapest to start.
* **ECS Fargate** (CPU/mem tuned; long jobs) with **EFS** if you need shared FS.
* **AWS Batch** for queue-based, containerized HPC/ML workloads and spot savings.

### Storage/transfer

* **S3 Transfer Acceleration** or **CloudFront Signed URLs** for global speed.
* **S3 Glacier** if you need long-term archiving of outputs.

# Dev vs Prod deployment shapes

**Development (Cheapest)**

* S3 + CloudFront (or Amplify Hosting)
* API GW (HTTP + WS) + Lambdas
* SQS, DynamoDB (on-demand)
* One ECS/Lambda worker only if needed
* Basic CloudWatch alarms

**Production (Hardened)**

* Cognito with fine-grained IAM to presign only for your users
* Step Functions to orchestrate multi-stage processing
* ECS Fargate or Batch for predictable, long jobs
* S3 Lifecycle policies, versioning, server-side encryption (SSE-S3/KMS)
* WAF on CloudFront + rate limiting
* Observability: CloudWatch dashboards, X-Ray tracing, structured logs
* Multi-AZ everything; DLQs with reprocessing; retries/backoff strategies

# Cost notes (rough)

* S3: \$0.023/GB-mo storage; requests a few cents. Free Tier includes 5GB/month + requests.
* API Gateway WS & HTTP: fractions of a cent per million msgs/requests; Free Tier covers some.
* Lambda: 1M free reqs + 400k GB-s; usually pennies.
* SQS: first 1M requests free/month.
* DynamoDB on-demand: pennies for low traffic.

(Heavy ECS/Batch compute, Transfer Acceleration, or huge CloudFront egress is where costs rise.)

# Frontend implementation tips

* Keep a `jobId -> progress` map in state.
* Use a **single** WS connection; send `subscribe` per job.
* If the WS drops, allow **resubscribe** and **poll** `GET /job-status?jobId=...` as a fallback.
* For big uploads, implement **multipart** with concurrency and retries.
* Auto-download: upon receiving `{downloadUrl}`, do:

  ```js
  const a = document.createElement('a');
  a.href = downloadUrl;
  a.download = '';
  document.body.appendChild(a);
  a.click();
  a.remove();
  ```
