# 4. webRTC server

## Purpose

This lab explains how to provide the server-side components required to use WebRTC in your application. It covers two hosting approaches you asked about: (A) EC2-hosted signaling + TURN (recommended for production) and (B) serverless signaling using API Gateway WebSockets + Lambda (possible but has limitations). The lab includes example code, deployment steps, testing instructions, and production notes.

## Objectives

- Explain the role of signaling and TURN servers in WebRTC
- Provide a minimal Node.js signaling server that can be hosted on EC2
- Show how to provision a TURN server (coturn) on EC2
- Describe a serverless alternative using API Gateway WebSockets + Lambda and DynamoDB
- Provide a test client and verification checklist

## Prerequisites

- An AWS account with permission to create EC2, IAM, API Gateway, Lambda, DynamoDB resources
- A domain name (recommended) or at least a public IP for your EC2 instance
- Basic Node.js knowledge (v16+ recommended) and familiarity with the AWS console or CLI
- Optional: certbot / Let's Encrypt for TLS on EC2 (recommended for wss:// and secure TURN)

## Quick architecture primer

- Signaling server: exchanges SDP offers/answers and ICE candidates between peers (can be WebSocket-based). It does not carry media.
- STUN: helps peers discover their public IP/port for NAT traversal (usually public STUN servers suffice).
- TURN: relay server used when direct peer-to-peer connection fails (requires a TURN server — long-lived, UDP/TCP/DTLS support). Recommended to run coturn on EC2 or use a managed TURN provider.

Choices:
- EC2: full control — host signaling (Node.js), host coturn, install TLS, easier for low-latency multi-protocol apps. Best for production and custom TURN.
- Lambda + API Gateway WebSockets: serverless signaling (good for scale & pay-per-use), but persistent UDP-based TURN cannot run in Lambda — you'll still need a TURN server (EC2 or managed). Lambda introduces cold-starts and limited connection durations for some websocket patterns.

## Option A — EC2: Node.js signaling server + coturn TURN server (recommended)

High-level steps

1. Launch an EC2 instance (Ubuntu 22.04 or similar).
2. Create a Security Group allowing ports:
	 - TCP 22 (SSH) from your IP
	 - TCP 80, 443 (HTTP/HTTPS) from 0.0.0.0/0 (for WebSocket over TLS)
	 - UDP/TCP 3478 (TURN/stun) from 0.0.0.0/0 (or restricted CIDRs)
	 - (Optional) UDP ephemeral range needed if you plan to allow relayed media - coturn handles allocation — 49152-65535 UDP recommended
3. SSH into the instance and install Node.js, git, NGINX (optional reverse-proxy), and coturn.
4. Deploy the Node.js signaling server and run it under PM2/systemd.
5. Configure TLS (Let's Encrypt) for your domain and make your signaling server use wss://
6. Configure coturn with credentials and TLS and run the service.

Example commands (Ubuntu) — adapt to your environment and keys

```bash
# update and install
sudo apt update && sudo apt upgrade -y
sudo apt install -y git curl build-essential

# Node.js (example using NodeSource)
curl -fsSL https://deb.nodesource.com/setup_18.x | sudo -E bash -
sudo apt install -y nodejs

# nginx (optional)
sudo apt install -y nginx

# coturn
sudo apt install -y coturn

# pm2 to manage the Node process
sudo npm install -g pm2
```

Minimal signaling server (Node.js + ws)

Create a directory `signaling` and a file `server.js` with the following minimal example. This simple server relays messages between connected clients by room/peer id. It's minimal and intended for learning — add auth and validation for production.

```js
// server.js
const WebSocket = require('ws');
const server = new WebSocket.Server({ port: process.env.PORT || 3000 });

// simple in-memory mapping: room -> Set of ws
const rooms = new Map();

server.on('connection', (ws) => {
	ws.on('message', (data) => {
		try {
			const msg = JSON.parse(data);
			// message: { type: 'join'|'signal', room, payload }
			if (msg.type === 'join') {
				const room = msg.room;
				if (!rooms.has(room)) rooms.set(room, new Set());
				rooms.get(room).add(ws);
				ws.room = room;
				return;
			}

			if (msg.type === 'signal') {
				const room = ws.room || msg.room;
				const peers = rooms.get(room) || new Set();
				// broadcast to others in same room
				for (const client of peers) {
					if (client !== ws && client.readyState === WebSocket.OPEN) {
						client.send(JSON.stringify({ type: 'signal', from: msg.from, payload: msg.payload }));
					}
				}
			}
		} catch (e) {
			console.error('invalid message', e);
		}
	});

	ws.on('close', () => {
		if (ws.room && rooms.has(ws.room)) {
			rooms.get(ws.room).delete(ws);
			if (rooms.get(ws.room).size === 0) rooms.delete(ws.room);
		}
	});
});

console.log('Signaling server started on port', process.env.PORT || 3000);
```

Run the server (development):

```bash
node server.js
# or using pm2
pm2 start server.js --name signaling
pm2 save
```

Notes — production hardening
- Use TLS and serve WebSocket over wss:// (nginx reverse-proxy + certbot is common)
- Add authentication (token-based, JWT) on connect
- Use Redis or another persistent messaging store if you need multiple signaling server instances
- Log messages and add rate-limiting to avoid abuse

### coturn setup (minimal)

```

use-auth-secret
static-auth-secret=YOUR_SECRET_KEY
realm=your-domain.example
total-quota=100
user-quota=50
no-multicast-peers
cert=/etc/letsencrypt/live/your-domain.example/fullchain.pem

```

```bash

sudo systemctl start coturn
```

## Option B — Serverless: API Gateway WebSockets + Lambda (signaling) + DynamoDB

Summary

- Use API Gateway WebSocket API for the websocket endpoint. Configure routes like `$connect`, `$disconnect`, and `sendMessage`.
- `$connect` and `$disconnect` are backed by Lambda functions that store/remove `connectionId` in DynamoDB.
- A `sendMessage` route triggers a Lambda which looks up the destination connectionId and calls the API Gateway Management API to post the message.
- Limitations: API Gateway WebSockets have their own scaling and throttling model, and using Lambda for frequent, low-latency signaling can introduce cold-start latency. Lambda cannot act as a TURN server — you'll still need a TURN service reachable by peers.

Minimal Lambda (Node.js) example for `sendMessage` route (simplified):

```js
// sendMessage.js
const AWS = require('aws-sdk');
const ddb = new AWS.DynamoDB.DocumentClient();

exports.handler = async (event) => {
	const body = JSON.parse(event.body);
	// body: { toConnectionId, payload }
	const apigw = new AWS.ApiGatewayManagementApi({
		endpoint: event.requestContext.domainName + '/' + event.requestContext.stage
	});

	try {
		await apigw.postToConnection({ ConnectionId: body.toConnectionId, Data: JSON.stringify(body.payload) }).promise();
		return { statusCode: 200 };
	} catch (err) {
		console.error(err);
		return { statusCode: 500, body: 'error' };
	}
};
```

Notes for serverless approach
- Use DynamoDB table keyed by `connectionId` to track metadata (room, userId).
- You still need STUN and TURN servers configured on the client RTCPeerConnection.
- This architecture is good for message-driven signaling and scales automatically, but be mindful of per-message costs and throttling limits.

## Client example (browser) — getUserMedia + RTCPeerConnection

This simple client illustrates how to use a signaling server to exchange SDP and candidates. Replace `SIGNALING_URL` and `TURN/STUN` config as needed.

```html
<!-- client.html (very minimal) -->
<button id="start">Start</button>
<video id="local" autoplay muted playsinline></video>
<video id="remote" autoplay playsinline></video>

<script>
const SIGNALING_URL = 'wss://your-domain.example/ws';
const ws = new WebSocket(SIGNALING_URL);

let pc;
const localVideo = document.getElementById('local');
const remoteVideo = document.getElementById('remote');

ws.onopen = () => console.log('connected to signaling');
ws.onmessage = async (ev) => {
	const msg = JSON.parse(ev.data);
	if (msg.type === 'signal') {
		const payload = msg.payload;
		if (payload.sdp) await pc.setRemoteDescription(payload.sdp);
		if (payload.candidate) await pc.addIceCandidate(payload.candidate);
	}
};

document.getElementById('start').onclick = async () => {
	pc = new RTCPeerConnection({
		iceServers: [
			{ urls: 'stun:stun.l.google.com:19302' },
			{ urls: 'turn:your-turn.example:3478', username: 'user', credential: 'pass' }
		]
	});

	pc.onicecandidate = (e) => {
		if (!e.candidate) return;
		ws.send(JSON.stringify({ type: 'signal', payload: { candidate: e.candidate } }));
	};

	pc.ontrack = (e) => (remoteVideo.srcObject = e.streams[0]);

	const localStream = await navigator.mediaDevices.getUserMedia({ audio: true, video: true });
	localVideo.srcObject = localStream;
	localStream.getTracks().forEach(t => pc.addTrack(t, localStream));

	const offer = await pc.createOffer();
	await pc.setLocalDescription(offer);
	ws.send(JSON.stringify({ type: 'signal', payload: { sdp: pc.localDescription } }));
};
</script>
```

Notes: the client sends/receives `signal` messages that include `sdp` or `candidate` objects. The signaling server should route these messages to the correct peer(s).

## Security, scaling, and costs

- Security:
	- Always use TLS for signaling (wss://) and TURN over TLS (tls/DTLS) when possible
	- Authenticate users before allowing access to signaling routes
	- Rate-limit signaling messages and validate payloads

- Scaling:
	- Signaling servers are relatively lightweight but require low-latency. Use multiple instances behind a load balancer and a shared state (Redis) for room mapping.
	- TURN servers are stateful and need capacity planning — run multiple coturn instances across AZs and use an elastic IP or load-balancer pattern for failover.

- Costs:
	- EC2: you pay for running instances (good for constant usage and when you need full control).
	- Lambda + API Gateway: pay per message/connection and for Lambda invocations — can be cheaper for bursty workloads but may become expensive for very frequent message flows.
	- Managed TURN providers (Twilio, Xirsys, etc.) add per-minute or per-GB charges — weigh against running your own coturn instances.
