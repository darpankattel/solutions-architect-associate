# 1 — High level architecture (what we'll build)

A nice fun project. This is a practical, copy-friendly guide to build **MyTodoApp** on AWS using serverless components with an eye for *\$0 / low cost practice* and a clear path to *industry grade* when you want to scale. I include step-by-step deployment choices, concrete IAM policy examples (copy/paste), caching and scaling options, thumbnail flow, email flow, and where to swap in production tech (DAX, Global Tables, WAF, etc.).

* Mobile app (iOS/Android/React Native) or web SPA.
* Authentication: **Cognito User Pool** (user sign-in) + **Cognito Identity Pool** (temporary AWS creds).
* REST API: **API Gateway** (HTTPS) → **Lambda** (business logic).
* DB: **DynamoDB** (todo items).
* File storage: **S3** (user folders / blog photos).
* CDN: **CloudFront** in front of S3 (and optionally API Gateway).
* Background: Lambda function triggered on S3 upload to create thumbnails.
* Email: **SES** (simple welcome email; sandbox considerations).
* Monitoring: **CloudWatch** logs & metrics; X-Ray optional.
* Low-cost practice options: run locally with SAM / LocalStack, or on AWS Free Tier with tiny usage.

# 2 — Cost-minimizing / practice setup (aim: \$0 or minimal)

Use these to avoid AWS bills while learning:

* Prefer local emulation:

  * **LocalStack** — emulates S3, Lambda, API GW, DynamoDB, Cognito (good for full offline tests).
  * **AWS SAM CLI** — run Lambdas and API locally.
* If you use AWS account (free tier):

  * DynamoDB: keep small item size and few R/Ws; use **On-Demand** for unpredictable small tests (but watch costs). Use provisioned with tiny RCUs/WCUs if tight.
  * Lambda: keep invocations low; remove provisioned concurrency.
  * S3 / CloudFront: keep small test files; invalidate sparingly (invalidation costs).
  * SES: sandbox requires verified addresses — use for dev emails only.
* Always set billing alerts and CloudWatch budget alarms.

If you want \$0 guaranteed for learning, prefer LocalStack + SAM + unit tests.

# 3 — Auth & direct S3 access (pattern)

We want users to authenticate and *directly* access their own S3 folder (no proxy through Lambda). Use:

1. **Cognito User Pool** — manage users, email verification, sign-in UI.
2. **Cognito Identity Pool** — exchanges tokens for temporary AWS credentials (IAM roles).
3. Create IAM roles:

   * **Authenticated Role**: limited S3/DynamoDB permissions constrained to the user's own resources via policy variables.
   * **Unauthenticated Role**: read-only / limited (optional).

Important claim variables:

* `cognito-identity.amazonaws.com:sub` is the identity id in Identity Pool.
* You can use `cognito-identity.amazonaws.com:amr` or `cognito-idp.amazonaws.com:username` if needed.

Example S3 policy below ensures each auth user only accesses `s3://mytodoapp-bucket/users/<identity-id>/*`.

# 4 — DynamoDB access pattern & read scaling

* Table: `Todos`

  * Partition key: `userId` (string)
  * Sort key: `todoId` (string) or `createdAt` timestamp for queries by time.
* Access pattern:

  * Mostly read: queries by `userId` for user’s todos (use Query not Scan).
  * For global reads / feed pages, consider GSI (e.g., `status` index) if needed.
* Scaling options:

  * **On-Demand** (good for dev/small) — auto scales but may cost more if heavy.
  * **Provisioned with Auto Scaling** (production) — set baseline R/W capacity then autoscale.
  * **DAX** (DynamoDB Accelerator) — add an in-memory caching layer for very high read throughput / microsecond latency.
  * **Global Tables** — multi-region, HA, low latency globally.
* Fine-grained IAM: restrict DynamoDB access so each user can only access their partition. Use `dynamodb:LeadingKeys` condition in IAM (example below).

# 5 — Caching strategy

* **At CDN layer**: CloudFront for static assets (S3) — long TTL for static content.
* **API response caching**:

  * API Gateway has built-in caching per stage & per method (cheap and easy). Cache GET responses, set TTL.
  * Or place CloudFront in front of API Gateway and cache GETs with appropriate Cache-Control headers.
* **DB caching**: DAX for DynamoDB (if heavy read traffic). Use DAX client from app/lambda.
* **Lambda-level**: use in-memory connection reuse and ephemeral caches (within same warm container) for reuse of DB clients.

# 6 — Thumbnail generation & welcome email flows

1. **Photo upload**: client uploads directly to S3 using temporary credentials. Upload location: `users/<userId>/uploads/`.
2. **S3 Event**: on `s3:ObjectCreated:*` trigger a Lambda that:

   * Downloads image, resizes (e.g., 200x200) via `sharp` (Node) or Pillow (Python).
   * Saves thumbnail to `users/<userId>/thumbs/<original>-thumb.jpg`.
3. **Welcome email**:

   * On user sign-up (Cognito User Pool trigger) or backend event, call SES to send welcome email.
   * SES in production needs verification & out of sandbox; for dev, use verified sender and recipient in sandbox.

# 7 — Concrete deployment steps (dev -> prod)

Minimal dev with AWS Free Tier:

1. Create Cognito User Pool (enable email sign-up) and Identity Pool (connect User Pool).
2. Create S3 bucket: `mytodoapp-bucket` (private).
3. Create DynamoDB table `Todos` (On-Demand).
4. Create a Lambda for API logic (Node/Python). Attach execution role (below).
5. Create API Gateway REST API:

   * Create resources `/todos` etc.
   * Attach Cognito User Pool Authorizer (so user must present token).
   * Integrate methods with Lambda proxy integration.
   * Enable CORS for mobile app origin.
6. Configure CloudFront distribution:

   * Origin 1: S3 bucket (static).
   * Origin 2 (optional): API Gateway (use custom cache behavior for GETs).
7. IAM: create roles/policies for:

   * Lambda execution (CloudWatch, DynamoDB access, S3 put/get for thumbnails).
   * Cognito authenticated role (S3 prefix + DynamoDB LeadingKeys policy).
8. SES: verify sender email. Use Lambda to send welcome email or set Cognito post-confirmation trigger.
9. Test with Postman / mobile.

Production extensions (see section 9).

# 8 — IAM role / policy examples

> Replace `123456789012` and `mytodoapp-bucket` and ARNs with your account/bucket names.

## 8.1 Cognito Authenticated Role (Identity Pool) — S3-only access to user's prefix

This policy grants read/write to `users/<identity-id>/*` where `${cognito-identity.amazonaws.com:sub}` binds to user's identity id.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowUserS3Access",
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::mytodoapp-bucket/users/${cognito-identity.amazonaws.com:sub}/*",
        "arn:aws:s3:::mytodoapp-bucket"
      ],
      "Condition": {
        "StringEquals": {
          "s3:prefix": "users/${cognito-identity.amazonaws.com:sub}/"
        }
      }
    }
  ]
}
```

Notes:

* `ListBucket` requires the bucket ARN (not the object ARN).
* For more robust listing, you may allow listing only limited prefixes in a Condition.

## 8.2 Cognito Authenticated Role — DynamoDB limited to user's partition (fine-grained)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowDDBForUser",
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:Query",
        "dynamodb:UpdateItem",
        "dynamodb:DeleteItem"
      ],
      "Resource": "arn:aws:dynamodb:us-east-1:123456789012:table/Todos",
      "Condition": {
        "ForAllValues:StringEquals": {
          "dynamodb:LeadingKeys": ["${cognito-identity.amazonaws.com:sub}"]
        }
      }
    }
  ]
}
```

* This requires your table partition key to be `userId` where you store the identity id as the leading key.

## 8.3 Lambda execution role (for API Lambda + thumbnail lambda)

Attach trust policy allowing Lambda service and these permissions:

```json
{
  "Version":"2012-10-17",
  "Statement":[
    {
      "Effect":"Allow",
      "Principal":{"Service":"lambda.amazonaws.com"},
      "Action":"sts:AssumeRole"
    }
  ]
}
```

Inline policy example for the thumbnail Lambda:

```json
{
  "Version":"2012-10-17",
  "Statement":[
    {
      "Effect":"Allow",
      "Action":[
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      "Resource":"arn:aws:logs:*:*:*"
    },
    {
      "Effect":"Allow",
      "Action":[
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource":[
        "arn:aws:s3:::mytodoapp-bucket/users/*/uploads/*",
        "arn:aws:s3:::mytodoapp-bucket/users/*/thumbs/*"
      ]
    },
    {
      "Effect":"Allow",
      "Action":[
        "sns:Publish",
        "ses:SendEmail",
        "ses:SendRawEmail"
      ],
      "Resource":"*"
    },
    {
      "Effect":"Allow",
      "Action":[
        "dynamodb:PutItem",
        "dynamodb:UpdateItem"
      ],
      "Resource":"arn:aws:dynamodb:us-east-1:123456789012:table/Todos"
    }
  ]
}
```

Adjust the SES/SNS permissions only if you use them.

Usually AWS sets this automatically when you create an integration; ensure your Lambda's resource policy allows invoke by API GW (managed by console/SAM).

# 9 — Production / industry-grade options (where to swap specs)

* **Authentication/Identity**:

  * Enable MFA in Cognito; use custom attributes if needed; enable advanced security (Cognito risk detection).
  * Consider external IdP (OKTA, Auth0, Google Workspace SSO) if enterprise.
* **API & Edge**:

  * Use **CloudFront + WAF** in front of API Gateway; add rate limits, geo-blocking, OWASP rules.
  * Use **Lambda\@Edge** or CloudFront Functions for authentication header manipulation or edge logic.
* **DynamoDB**:

  * Use **Provisioned Capacity + AutoScaling** for predictable cost and DAX for microsecond reads.
  * Use **Global Tables** across regions for HA and low latency worldwide.
* **S3 / Media**:

  * Use S3 Replication (CRR) for cross-region durability.
  * Use Lambda Layer or a containerized image builder for high-performance image processing (or use Elastic Transcoder / MediaConvert).
* **Email**:

  * Move SES out of sandbox; also consider transactional email providers (SendGrid, SES dedicated IPs).
* **Observability**:

  * Use CloudWatch Logs Insights, X-Ray tracing, and a centralized dashboard (Grafana, Datadog).
* **CI/CD & IaC**:

  * Infrastructure as Code: **Terraform** or CloudFormation / CDK.
  * CI: GitHub Actions / CodePipeline to deploy SAM/CloudFormation stacks.
* **Security**:

  * Use **VPC endpoints** for S3/DynamoDB access from Lambda in a VPC.
  * Use **KMS** to encrypt sensitive data.
  * Implement least privilege IAM and Secrets Manager for secrets.
* **Resilience**:

  * Multi-AZ for RDS (if using), multi-region for DynamoDB, backups (Point-in-time backups).
* **Cost optimization**:

  * Reserved capacity for DynamoDB/DAX, use savings plans where possible.

# 10 — Example API endpoints (recommended)

* `POST /todos` — create todo (userId from token)
* `GET /todos` — list user's todos (Query by `userId`)
* `GET /todos/{todoId}` — get single
* `PUT /todos/{todoId}` — update
* `DELETE /todos/{todoId}` — delete
* `POST /upload-url` — return pre-signed S3 PUT URL (if you prefer pre-signed pattern)

Set API Gateway methods to use Cognito Authorizer so `Authorization: Bearer <id_token/access_token>` is required.

# 12 — Security checklist

* Lock down S3 bucket policy (block public access).
* Use HTTPS everywhere (API Gateway automatically uses TLS).
* Use Cognito authorizer on API methods.
* Audit IAM roles; enable CloudTrail.
* Enable CORS only for allowed origins.
* Harden CloudFront with WAF and TLS1.2+ policies.
* Use least-privilege IAM (examples above).

# 13 — Helpful tools & suggestions for \$0 practice

* LocalStack (emulate AWS locally).
* AWS Free Tier (watch quotas).
* AWS SAM + `sam local start-api` for local lambda testing.
* Use small sample data, avoid logs retention long (set retention to 1 week).
* Use pre-signed URLs for S3 uploads to avoid giving broader rights.
* Use Cognito hosted UI for quick login flow.

# 14 — Quick checklist to launch a minimal working prototype (10–20 minutes once accounts exist)

1. Create S3 bucket `mytodoapp-bucket` (private).
2. Create Cognito User Pool + Identity Pool.
3. Create DynamoDB `Todos` (On-Demand).
4. Create Lambda `api-handler` with minimal CRUD code and attach role (see role sample).
5. Create API Gateway, integrate with Lambda, add Cognito Authorizer for methods.
6. Test login, obtain tokens, call APIs.
7. Add S3 pre-signed upload flow or Identity Pool role to allow direct S3 PUT for user prefix.
8. Add CloudFront distribution later to front S3.
